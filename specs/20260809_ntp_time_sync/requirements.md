# 需求规格说明书：定时任务插件与 NTP 自动对时

> 状态：已确认

日期：2026-08-09
Feature：ntp_time_sync
阶段：Phase 1

## 背景

Focus Clock 已具备 DS1302 RTC、按需 WiFi 和 `OFF/AUTO` 联网策略，但尚无可复用的定时业务调度能力，也无法定期校正 RTC 漂移。本期需要先建立可供后续任务复用的轻量插件生命周期和每日调度能力，再以每天中国本地时间 08:00 的 NTP 自动对时作为第一个插件。

## 目标

- 提供编译期注册、固定容量、非阻塞的任务插件执行与每日调度能力。
- 让插件生命周期、调度触发和资源租约彼此分离，后续任务可复用执行契约或增加新的调度任务。
- 仅在每天本地时间 08:00 所在分钟触发一轮 NTP 对时，不对错过的触发进行补执行。
- 在不破坏 Portal、输入、计时、显示和低功耗策略的前提下，按需申请 WiFi、校准 DS1302，并展示最后成功结果。

## 功能需求

### R-01：可复用的插件执行契约

当固件集成需要异步推进的后台插件时，系统应当提供稳定任务标识、启动、主循环更新、运行中和终态结果的轻量契约，并明确由插件拥有和释放其申请的资源。

首期契约应满足：

- 编译期确定插件集合和固定容量，不进行运行时安装、卸载或动态加载。
- 插件执行生命周期不依赖具体 UI、屏幕唤醒或偶然的 WiFi 连接事件。
- 调度器只判断和派发，不包含 NTP 重试等插件业务逻辑。
- 首期只有 NTP 插件时允许用稳定 ID 明确分发；接口边界应允许后续增加其他插件或触发来源，而不要求本期提前实现动态注册表。

### R-02：每日定时调度

当 RTC 有效、当前本地时间处于任务配置的精确分钟、该任务今天未运行且未完成时，系统应当启动该任务的一轮执行。

调度能力应满足：

- 支持编译期配置的每日本地时间任务；首个任务写死为中国本地时间 08:00，本期不支持用户配置。
- `08:00:00..08:00:59` 内首次观察到有效 RTC 时间时可以派发；若设备直到 08:01 或更晚才运行或读到 RTC，则当天不补执行。
- 调整 RTC 时间、任意 WiFi 连接事件或其他业务事件不得形成补充触发源。
- 任务运行中不得重复派发。
- 一轮最终成功或失败后，当天不得再次自动派发，次日本地日期恢复执行资格。
- RTC 无效时不得猜测日期或派发每日任务。

### R-03：调度记录持久化与重启恢复

当一轮任务准备派发时，系统应当先持久化足以防止当天重复执行的本地日期键，再启动插件，使主循环继续运行或设备当天重启后不会因再次读到 08:00 而重复执行。

当 NTP 校正导致本地日期发生变化时，系统应当使用写入后回读的 RTC 日期作为完成日期。

当任务在派发后、进入终态前重启时，系统应当把该日期视为已经尝试，不恢复或重新派发中断的一轮。

### R-04：NTP 插件按需申请网络

当每日对时任务开始时，NTP 插件应当以独立 consumer 向现有 WiFi service 申请自动网络，并在所有成功、失败、超时或取消终态释放该 consumer。

网络申请应满足：

- `WIFI=OFF` 或无有效 STA 凭据时不打开 STA，本轮直接结束。
- `WIFI=AUTO` 且凭据有效时，等待现有 WiFi service 建立 STA 连接。
- WiFi 获取使用任务自身的有限总 deadline，不跟随 service 的后台重连无限等待。
- Portal 同时运行时允许形成 `AP_STA`；释放 NTP consumer 不得关闭 Portal 仍需要的 AP 或其他 consumer 的 STA demand。
- consumer 活动期间复用现有 `networkTaskActive` 阻止 Light Sleep，释放后恢复原有休眠判断。

### R-05：非阻塞 SNTP 同步和有限重试

当 STA 已连接时，NTP 插件应当异步启动 SNTP 并在主循环中观察本轮同步结果，不得使用长时间阻塞等待。

同步过程应满足：

- 使用配置的多个 NTP server 发起一次 SNTP attempt。
- 只有收到本轮 SNTP 完成信号后才读取系统时间，不得把上次残留的有效系统时间当成本轮成功。
- 单次 attempt 超时后显式停止本轮 SNTP，经过非阻塞重试间隔后重新发起。
- 每轮最多执行两个 SNTP attempt；第二次失败后以最终失败结束当天任务。
- 成功或最终失败后停止本轮 SNTP，避免之后临时联网引发未受控后台同步。
- 所有 `millis()` deadline 和重试间隔判断在计数器回绕时仍正确。

### R-06：中国标准时间转换与校验

当本轮 SNTP 完成时，系统应当按固定 UTC+8、无夏令时规则取得中国本地时间并转换为 `RtcTime`。

转换结果应满足：

- 年份在 DS1302 支持的 `2000..2099` 范围内。
- 年、月、日、时、分、秒组合合法。
- 星期正确映射到 DS1302 使用的 `1..7`。
- 无效或越界的时间不得写入 RTC，也不得更新最后成功结果。

### R-07：DS1302 写入、回读和结果判定

当取得合法的本地 NTP 时间时，插件应当写入 DS1302 并通过 RTC service 强制回读确认。

只有写入成功、回读成功且回读值有效时，系统才应当把本轮判为成功。RTC 只写入一次；写入或回读失败时，不得更新最后成功对时时间，也不得重试 RTC 写入或重新请求 NTP。

### R-08：最后成功对时时间持久化

当 RTC 写入和回读确认成功时，系统应当持久化最后成功同步的 UTC epoch，并在重启后恢复该值。

系统只持久化调度完成日期和最后成功 epoch；瞬时状态、失败原因和重试进度只保存在 RAM 中。

### R-09：远程设置页只读展示

当用户打开 WiFi 配置 Portal 时，系统应当通过现有配置读取 API 返回最后成功对时信息，并在页面以只读方式展示。

展示应满足：

- 从未成功同步时展示 `never`。
- 已成功同步时按固定 UTC+8 展示本地日期和时间，不受访问设备浏览器时区影响。
- 本期不提供对时时间、启停状态、时区或立即同步的编辑控件。

### R-10：主循环和现有功能协调

当调度或 NTP 插件处于等待、重试或联网阶段时，系统应当持续推进输入、Timer、RTC、WiFi Portal、显示反馈和物理 Cancel 处理。

调度与插件应当按明确顺序接入现有主循环，使任务可以在 WiFi service 更新前申请网络，并在 WiFi service 更新后观察最新连接状态和推进状态机。

### R-11：运行状态可诊断

当 NTP 任务运行或结束时，系统应当保留足够的 RAM 状态和受控串口日志，以区分等待网络、等待 SNTP、RTC 写入、成功及主要失败原因，且不得输出 STA 密码等敏感信息。

诊断能力不要求本期在 Portal 展示完整失败历史。

### R-12：RTC 无效时的故障展示

当 DS1302 读取无效时，系统应当保持 `rtcOk=false` 和 `RtcTime.valid=false`，不得用编译时间、固定时间或其他猜测值写入 RTC。

时钟显示区域应当使用固定 `12:00` 作为故障回退值，方便用户识别 RTC 异常；状态区域仍应明确展示 RTC 读取失败。后续重启或 RTC 自身恢复并读到有效值时，系统应当自然恢复正常显示和每日调度。

## 非功能需求

### NFR-01：响应性

网络连接、SNTP 等待和重试不得通过长 `delay()` 阻塞主循环。现有 `rtcSetTime()` 的短同步写后确认可保留，但真机验收时不得造成可感知的输入或 HTTP 停顿。

### NFR-02：资源约束

调度与插件运行态应使用固定容量和值类型，不引入动态插件加载、后台 RTOS task 或为单个插件设计的复杂虚函数体系。

### NFR-03：可复用性

插件执行契约、每日到期判断、日期键、溢出安全 deadline 和资源所有权边界应与 NTP 业务解耦。后续新增任务应能复用这些能力，而无需复制当日去重、主循环轮询或 WiFi 租约规则。

### NFR-04：可测试性

日期调度、任务终态、时间转换、deadline、重试状态转换和持久化编解码应尽量提取为不依赖 Arduino 的纯逻辑，并由宿主测试覆盖。固件集成还需执行页面脚本语法检查和 PlatformIO 构建。

### NFR-05：持久化耐久性

每个每日任务每个本地日期最多写入一次完成记录；运行中状态变化和失败原因不得持续写 NVS。

### NFR-06：兼容性与最小影响面

新增能力不得改变现有 `OFF/AUTO` 策略、WiFi Portal 生命周期、夜间息屏配置语义或 Light Sleep 门禁来源。RTC 无效时移除编译时间自动写入，但保留短周期读取和恢复后的自然回归。

## 验收标准 / 人工确认点

### AC-01：精确分钟触发且不补执行

Given RTC 有效且 Time Sync 今天未完成
When RTC 在 `08:00:00..08:00:59` 内被主循环观察到
Then 系统启动且只启动一轮 Time Sync；若首次观察时已到 08:01 或更晚，则当天不执行

### AC-02：当日去重和重启恢复

Given Time Sync 今天已最终成功或失败并持久化完成日期
When 主循环继续运行或设备在同一天重启
Then 系统不再派发 Time Sync，并在本地日期变化后恢复执行资格

### AC-03：策略拒绝

Given WiFi 策略为 `OFF` 或 STA 凭据未配置
When Time Sync 到期
Then STA 不被打开，本轮进入最终失败，consumer 被释放且当天不重复执行

### AC-04：同步成功

Given WiFi 策略为 `AUTO`、凭据有效且 NTP 可访问
When Time Sync 到期并收到本轮 SNTP 完成信号
Then 合法的 UTC+8 时间被写入并回读 DS1302，最后成功 epoch 被保存，任务完成日期采用回读后的 RTC 日期

### AC-05：旧系统时间隔离

Given ESP32 系统中保留了看似有效的旧时间
When 本轮 SNTP 尚未收到完成信号或已经超时
Then 系统不得写 RTC，也不得更新最后成功 epoch

### AC-06：超时与资源释放

Given WiFi、DNS/NTP、RTC 写入或回读发生失败
When 本轮 deadline 或有限重试耗尽
Then 插件进入最终失败、停止 SNTP、释放自己的 WiFi consumer，并恢复符合其他 demand 的无线和 Light Sleep 状态

### AC-07：并发 Portal

Given 配置 Portal 正在运行
When Time Sync 同时申请和释放网络
Then AP、HTTP、物理输入和 Portal 生命周期保持可用，NTP 任务只影响自身 STA demand

### AC-08：页面展示

Given 设备从未成功对时或已经有持久化成功 epoch
When 用户打开 Portal
Then 页面分别展示 `never` 或固定 UTC+8 的最后成功日期时间，且没有可编辑对时控件

### AC-09：交互响应

Given Time Sync 正在等待 WiFi、SNTP 或重试
When 用户操作旋钮、按钮、Timer 或 Portal
Then 现有交互持续响应，页面元素不重叠，HTTP 和显示无明显停顿

### AC-10：自动化覆盖

Given 功能实现完成
When 执行宿主测试、Web 脚本语法检查和 PlatformIO 构建
Then 自动化用例覆盖调度边界、当日去重、重启恢复、日期修正、策略拒绝、状态机成功/超时/重试、旧时间隔离、RTC 失败、consumer 释放和 `millis()` 回绕；构建确认所用 SNTP API 与目标框架兼容

### AC-11：RTC 故障回退

Given DS1302 读取无效
When 时钟页面渲染或设备继续轮询 RTC
Then 时钟区域展示固定 `12:00`、状态区域展示 RTC 故障，固件不向 DS1302 写入猜测时间；后续读到有效 RTC 时恢复正常行为

## 范围外

- 运行时安装、卸载或动态加载插件。
- 通用插件市场、脚本运行时、动态依赖注入或跨固件 ABI。
- 用户配置任务时间、启停状态、时区或 NTP server；首期中国本地时间 08:00 写死在固件中。
- cron 表达式、每周、每月或复杂日历规则。
- 多时区和夏令时规则。
- 因任意 WiFi 连接成功而自动触发对时。
- 修改夜间息屏时间时联动修改每日对时时间。
- RTC 无效时开机联网修复、猜测当前日期或向 DS1302 写入默认时间。
- Portal 中的“立即同步”操作、完整失败历史或失败通知。
- 基于下一任务时间新增 RTC alarm 或改变首期最长约 30 秒的 RTC 刷新兜底。

## 待确认问题

### 阻塞性问题

无

### 非阻塞假设

- A-01：将“插件可复用”解释为复用固定容量的生命周期、结果、资源所有权和调度纯逻辑，不在只有一个插件时实现动态注册表或通用插件平台。（后续可调整点：出现第二类插件或非定时触发后，可基于稳定 ID 演进为编译期描述表。）
- A-04：WiFi 总等待 20 秒、单次 SNTP 等待 10 秒、重试间隔 3 秒，每轮最多两个 SNTP attempt。（后续可调整点：集中为编译期配置常量，不提供用户设置。）
- A-02：最后成功对时精确到秒，Portal 展示格式采用 `YYYY-MM-DD HH:MM:SS`。（后续可调整点：仅影响格式化与页面文案，不改变持久化 epoch。）
- A-03：串口诊断沿用 `ENABLE_SERIAL_LOGGING`，不新增用户可配置日志级别。（后续可调整点：未来可独立设计诊断级别。）
